# 高级 RAG 与安全 SQL 分析

## 评估结论

原有政策检索适合单一关键词问题，但有两个明显边界：只按词集合重叠排序，复合
问题不保证覆盖每个子主题；最高分超过阈值也不能证明答案覆盖了用户问题。因此
本阶段保留本地、可解释、无需外部语料的原则，升级为混合检索，而不是为三个
原创 Markdown 文件引入远程向量数据库。

直接开放 text-to-SQL 不符合本演示的授权模型。即使模型只生成 `SELECT`，它仍
可能选择敏感列、遗漏 actor 范围、构造昂贵连接或利用数据库方言。因此实现的是
“模型生成分析规范，服务端编译 SQL”，不执行模型文本。

## 混合政策检索

检索器组合以下信号：

- 归一化 token、英文词形别名和中英文概念扩展；
- IDF 加权的词项覆盖；
- 标题/章节命中提升；
- 字符三元组相似度；
- 面向复合问题的贪心证据覆盖重排。

最终答案仍是来源章节的抽取式摘要，并返回结构化引用。除最低相关分外，还要求
已选章节覆盖至少 55% 的查询概念；“提交截止时间和飞船停车规则”即使命中前半
部分也会拒答。工具事件公开 `hybrid` 模式、最高置信度和证据覆盖率，便于评估。

## 安全 SQL Agent

```mermaid
flowchart LR
    U["自然语言分析问题"] --> P["AnalyticsQuerySpec"]
    P --> V["Pydantic 枚举与边界校验"]
    V --> A["Core API actor 范围"]
    A --> C["SQLAlchemy 参数化编译"]
    C --> R["SQLite query_only 连接"]
    R --> O["最多 50 行分组结果"]
```

允许的维度只有项目、状态、员工、工作日期和月份；指标只有总工时和记录数。
过滤器只允许日期、状态、项目 ID 和可见员工 ID，排序与 limit 也有枚举/上限。
请求 Schema 没有 SQL 字符串、表名、列名、函数、JOIN 或表达式字段。

Core API 在执行时始终加入 `visible_employee_ids(actor)`，指定员工还会调用现有
记录级授权检查。SQLAlchemy 负责编译参数；SQLite 连接在该次执行期间设置
`PRAGMA query_only=ON`，进度处理器把单次查询限制在 1 秒执行预算内。原始 SQL
形状的对话在 Agent 层直接拒绝，不调用 Core。

## 仍然不等于生产方案

当前数据量很小，单语句与 50 行上限足够演示。生产化还需要数据库独立只读账号、
数据库侧资源/成本预算、查询审计、并发隔离、PostgreSQL RLS、Schema 迁移版本，
以及针对更大语料的离线检索评估。不能因为当前 Agent 名为“安全 SQL”就跳过这些层。
